# AB2044 — Content authority and ALM technical design

Status: Proposed for Level-A acceptance
Decision owner: Max Maraj
Owning work item: [AB2044](https://dev.azure.com/maxpowerplatform/MPP/_workitems/edit/2044)
Repository: [MaxPowerPlatformWebsite](https://github.com/Max-Power-Platform/MaxPowerPlatformWebsite)
Baseline: `dev` at `daf3dc5c9009ff3130c5b27ff014d9566caf93ca`
Decision date: 2026-08-06

## Decision

Adopt option C: a controlled, repository-first hybrid with one-way reconciliation.

The authoritative product source is the reviewed Git tree under
`src/portal/mpp2---mpp2/`. Within that tree, authority is divided by artifact class:

1. `scripts/Build-Site.ps1` is the authoring authority for the artifacts it generates.
2. A committed portal file is the authoring authority when it is outside the generator's
   declared output set.
3. Power Pages Studio is never an independent source authority. A Studio export is drift evidence
   that must be reconciled into the applicable generator input or hand-authored Git file through a
   task branch and pull request.

There is no second deployable source tree. `src/website/` is a stale path and must not be created,
uploaded, merged, or treated as recovery state.

This decision is design-only. It does not authorize a Studio edit, PAC command, pipeline run,
portal upload, deployment, restart, Dataverse write, identity change, service connection, tenant
change, or environment mutation.

## Why this option

The baseline repository contains only `src/portal/`; it has no `src/website/` directory.
`Build-Site.ps1` already defines the module catalog and rewrites shared, cross-page content. Other
assets, including the operating-system JavaScript and CSS, are explicitly hand-authored. A pure
Studio-first model would discard the executable generator contract. A pure generator model would
misrepresent the hand-authored portal artifacts. The controlled hybrid preserves both without
giving two systems authority over the same file.

The alternative options are rejected:

- Option A, an unrestricted generator-first model, is rejected because `Build-Site.ps1` does not
  generate every portal artifact.
- Option B, Studio/export-first, is rejected because the current download and upload scripts target
  nonexistent `src/website/`, while the shipped source and generator target `src/portal/`.
- A bidirectional or "last writer wins" hybrid is rejected because it cannot prevent silent
  overwrites between Studio, obsolete scripts, and `Build-Site.ps1`.

## Artifact ownership

### Generated by `Build-Site.ps1`

The generator owns these artifact classes:

- module and Managed M365 page records that it creates when absent;
- content-page HTML for every module in its `$modules` catalog;
- Managed M365 content-page HTML;
- Home page content;
- the Default navigation weblink set;
- the Footer content snippet;
- the YAML registration records for `mpp-os.js` and `mpp-os.css` when absent.

Changes to those outputs must start in `Build-Site.ps1`. A pull request must include the resulting
generated diff. Direct edits to a generated output are forbidden because the next generator run can
replace them.

### Hand-authored Git source

Files under `src/portal/mpp2---mpp2/` not in the declared generator output set are edited directly
in Git. This includes the content bytes of `mpp-os.js` and `mpp-os.css`, images, Liquid/web
templates, site settings, permissions, roles, and portal records not explicitly generated above.

When a hand-authored file is referenced by generated markup, the source change and the generator
reference change belong in the same Story, branch, and pull request.

### Studio exports

Studio is a visual editor and diagnostic surface, not a source authority. A permitted Studio change
must follow this direction:

```text
Dev Studio snapshot -> isolated export -> reviewed diff -> generator input or hand-authored file
                    -> task branch -> PR to dev
```

An export must not write directly over the canonical tree. It must land in a disposable or
explicitly ignored comparison location. Generated-surface differences are re-expressed in
`Build-Site.ps1`; hand-authored differences are selectively applied to their owning files. The
canonical tree is never overwritten wholesale by an environment download.

## Script disposition

| Component | Decision | Required implementation |
|---|---|---|
| `scripts/Build-Site.ps1` | Retain as the sole generator for its declared output set. | Declare outputs mechanically, remove runtime GUID creation, and make normalized no-diff generation provable. |
| `scripts/Update-Content.ps1` | Obsolete competing content generator. | Remove it or replace it with a fail-closed deprecation stub that points to `Build-Site.ps1`. |
| `scripts/Generate-ModulePages.ps1` | Obsolete competing page generator. | Remove it or replace it with a fail-closed deprecation stub. Page creation moves behind `Build-Site.ps1` with stable IDs. |
| `scripts/Generate-Nav.ps1` | Obsolete competing navigation generator. | Remove it or replace it with a fail-closed deprecation stub. Navigation remains owned by `Build-Site.ps1`. |
| `scripts/pages-download.ps1` | Unsafe until reconciled; targets `src/website/`. | Change it to export into an isolated comparison directory and fail if asked to overwrite the canonical tree. |
| `scripts/pages-upload.ps1` | Nonfunctional for the canonical source; targets `src/website/`. | Change it to upload only `src/portal/mpp2---mpp2/` after repository and environment gates pass. |
| `.github/workflows/pages-export.yml` | Unsafe scheduled shadow-source writer. | Disable the schedule until the isolated-export reconciliation flow and prover are implemented. Never auto-merge drift. |
| UAT/Prod deployment workflows | Manual and currently point through the stale upload wrapper. | Keep non-runnable for release claims until the wrapper, approvals, environments, and evidence contract are reconciled in a separate envelope. |

The obsolete generators must not remain silently executable against canonical files. Their removal
or fail-closed behavior is an implementation acceptance condition.

## Identifier and determinism contract

At the baseline commit, three consecutive repository-only runs showed stable generated bytes after
the existing records were present. The third-run SHA-256 values were:

| Generated artifact | SHA-256 |
|---|---|
| Footer snippet | `A6E2181692835F1B45C7CA6221F0379293A87A11220B2A08AD696938DC382ECD` |
| Home page content | `626E5A7B38C4A7B409D8F2B50FADBB40903FB73CB1936471B7B5B6F98589F972` |
| Default navigation | `64E671635C1E9E7A5EFDEC54BF6F66349C59426BBE0630B5BA8AF313A53FD767` |

That is not complete determinism. `Build-Site.ps1` calls `[guid]::NewGuid()` when page, web-file,
annotation, or navigation records are missing. The same logical source can therefore produce
different first-run IDs. The implementation must replace runtime ID generation with committed,
stable identifiers derived from an explicit manifest. Missing or duplicate identifiers must fail
closed; the generator must never heal them with a new random ID.

Line endings are also cosmetically unstable on the Windows baseline: Git can report stat-dirty
files while the normalized diff is empty. Determinism checks must compare normalized content and
must then refresh the index before interpreting status. A false dirty result must not be treated as
content drift.

## Branch and release authority

- Task work uses one Story, one task branch, and one pull request.
- Task branches start from current `dev` and target `dev`.
- `dev` is the integration authority for accepted website source.
- `main` is the release branch and may receive only an approved promotion from `dev` or an approved
  release hotfix.
- `master` is obsolete and must not receive new work.
- A branch, commit, or PR is source evidence; Azure Boards remains delivery, checkpoint, approval,
  blocker, and recovery authority.

GitHub currently reports `main` as the default branch even though repository governance requires
PRs to `dev`. The repository also retains `main` and `master` at the older migration commit
`429558c`. A later repository-settings envelope must change the GitHub default to `dev`, confirm
branch protection, and archive or clearly freeze `master`. This TDD does not authorize those
settings changes.

## Environment and release boundaries

Source direction is:

```text
task branch -> PR -> dev -> separately approved UAT release -> separately approved Production release
```

No branch push or merge implies an environment release. Each release requires its own owning work
item, exact commit, target environment, artifact/source hash, approval, rollback, and live browser
evidence. Dev, UAT, and Production must use separately named identities and environment controls.
No local or CI command may infer a tenant, environment URL, website ID, or credential from the
current interactive context.

The current documentation contains direct-to-Production and Studio-first instructions. Those are
historical contradictions and must be corrected by the implementation PR before any workflow is
enabled or used.

## Test-first implementation contract

The implementation must first add a non-mutating `scripts/Test-ContentAuthority.ps1` prover with
focused tests. It must fail on each of these fixtures before the implementation and pass afterward:

1. A deployable `src/website/` tree exists.
2. Executable guidance or workflow paths target `src/website/`.
3. Guidance declares Studio, exported files, or a second script authoritative for a generated
   artifact.
4. A generated output is edited without the owning generator input changing.
5. An obsolete generator can write to the canonical tree.
6. A logical record lacks a stable ID, reuses an ID, or obtains an ID at runtime.
7. Two normalized generator runs produce different file sets or bytes.
8. Download automation can overwrite the canonical tree.
9. Upload automation points anywhere except the exact canonical site directory.
10. Repository guidance disagrees about task base/target, integration branch, release branch, or
    environment direction.
11. `SESSION_HANDOFF.md` contains active-session state or is described as recovery authority.

The prover must:

- perform no network, PAC, Azure, Dataverse, portal, pipeline, or environment operation;
- use a temporary copy for generator execution;
- compare normalized bytes and exact file inventories;
- print actual versus expected for every gate;
- name every conflicting file and rule;
- return nonzero on any contradiction; and
- run in governance CI on pull requests to `dev` and `main`.

The first implementation PR must make the prover green by reconciling, at minimum:

- `README.md`;
- `docs/EDIT-WORKFLOW.md`;
- `docs/DEPLOYMENT.md`;
- `docs/ENVIRONMENTS.md`;
- `docs/BACKLOG.md`;
- `docs/WEBSITE-UPDATE-PLAN.md`;
- `docs/SPRINT-PLAN.md`;
- `docs/TDD.md`;
- `.github/copilot-instructions.md`;
- the three obsolete generators;
- both page transfer scripts; and
- the page export and deployment workflows.

`SESSION_HANDOFF.md` remains a deprecation pointer only. It must not be expanded or used to carry
this decision's current state.

## Security, identity, tenant, data, and deployment contract

- Repository source and design are the only surfaces authorized by AB2044.
- No environment may be read or written to prove this design.
- No identity, permission, secret, certificate, federated credential, environment variable,
  service connection, or GitHub environment may be created or changed.
- No Power Pages Studio, PAC upload/download, cache clear, restart, publish, Dataverse request, or
  pipeline execution is permitted.
- Portal metadata, web roles, table permissions, site settings, and user data are out of scope.
- Any later source implementation must preserve source IDs and permissions unless its own accepted
  contract names them.

## Sequencing and dependencies

1. Accept this TDD at an exact commit.
2. Implement the offline authority prover and stable-ID manifest first.
3. Quarantine obsolete generators and reconcile documentation and transfer scripts.
4. Reconcile GitHub default/protection settings in a separately recorded repository-settings
   envelope.
5. Only after steps 1–4 pass may shared Home, navigation, footer, or generated module work begin.
6. AB2049 and AB2050 may gather decision evidence in parallel, but they must not mutate shared
   generated content before this contract is implemented and green.

Changes to `Build-Site.ps1`, Home, navigation, Footer, shared page templates, or the canonical
source path are serialized through the owning Azure Boards item. Work on a hand-authored isolated
asset may proceed in parallel only when its write set does not overlap those surfaces.

## Evidence and acceptance

AB2044 is ready for Level-A TDD review when the branch contains only this design artifact and the
following evidence is attached to the work item:

- baseline and final commit;
- inventory proving `src/portal/mpp2---mpp2/` is the only committed portal source;
- the stale `src/website/` references and conflicting guidance named above;
- deterministic repeated-run hashes and the runtime-GUID gap;
- GitHub branch/default-branch read-back;
- repository governance validation result; and
- pull request to `dev` with no deployment or environment check claimed as release evidence.

Level-A acceptance approves the architecture decision only. It does not approve the implementation
batch, PR merge, workflow execution, or any environment operation.

## Rollback

Before implementation, rollback is `git revert` of the TDD commit and restoration of AB2044's prior
design status. After implementation, rollback is a revert of the exact implementation PR followed
by the last accepted version of the offline authority prover. No environment rollback is part of
AB2044 because AB2044 permits no environment mutation.
